## 2026-05-14 — horus — Cascade D — Python 3.12+ paren-less multi-exception `except` is the CANONICAL ruff-format style

- **Insight (revised — see end)**: Python 3.12+ accepts `except A, B, C:` (no parentheses around the multi-exception tuple) as **valid syntax** that catches all three exception types correctly. Looks identical to deprecated-removed Python 2 syntax (`except A, e:` where `e` was a binding alias) but behaves correctly as a 3-tuple of exception classes. **CRITICAL FINDING**: `ruff format` (the canonical Python 3.12+ formatter, mimics Black) ACTIVELY PREFERS the paren-less form. Wrapping in parens `except (A, B, C):` triggers `ruff format` to REVERT to `except A, B, C:` (verified empirically via `ruff format --diff`). So `except A, B, C:` is the CANONICAL ruff/Black style for Python 3.12+, NOT a footgun, NOT a Python 2 leftover. Discovered during ADR-009 PR(b) Step 2 prep: scanning `src/horus/vlm_extractor.py:434` flagged what looked like a SyntaxError that should have blocked import — but `ast.parse`, `import`, `ruff check`, `ruff format --check`, `mypy --strict`, AND `make test` (39 green) all passed cleanly. Empirical confirmation: each of AttributeError / ValueError / KeyError gets caught; RuntimeError does not.
- **Source**: HORUS commit `ab6b39c` (ADR-009 PR(a) Step 2 — `vlm_extractor.py` dispatcher creation); investigated at ADR-009 PR(b) start (2026-05-14). Edit attempt to "fix" the code was REVERTED by ruff format on the next make-format invocation, leading to the canonical-style discovery.
- **Project**: HORUS (Cascade D); generalizes to any Python 3.12+ codebase using ruff/Black.
- **Cascade**: D
- **Date observed**: 2026-05-14
- **Proposed L1 change** (revised after empirical investigation):
  - Update `no-half-knowledge` rule (or add a "Python 3.12+ syntax surprises" appendix) with a note: "Python 3.12+ accepts paren-less multi-exception except clauses as tuple-of-classes. ruff/Black ACTIVELY PREFER this form. Do NOT treat `except A, B, C:` as a Python 2 leftover; it is the modern canonical form. Confirm with `ruff format --diff` before flagging."
  - Codify the "verify-canonicality-before-fixing-style" empirical-test pattern in `make-sure-it-works` rule (the canonical 2-step empirical test: (1) `python -c "import ast; ast.parse(open(path).read())"` — if clean, syntax is valid; (2) `ruff format --diff path` — if no diff produced, code is already canonical-formatted). Applies to ANY suspected style issue, not just exception-handler style.
  - **Withdraw** the earlier proposal to "add a ruff rule that flags paren-less multi-exception except clauses" — that proposal was wrong (would conflict with ruff format's own preference). Open question: SHOULD ruff/Black prefer the paren-less form? That's an upstream design question, not a HORUS rule question.
- **Pairs with**: `make-sure-it-works` (empirical verification before claim, NOT just code-style instinct); `no-half-knowledge` (full-trace verification including the canonical-formatter check, not just "this looks broken"); `be-honest-direct-critical` (the discipline that flagged "this looks broken", investigated, found I was wrong, and updated the queue entry — instead of doubling down).
- **Severity**: Low for the code itself (works correctly + is canonical); HIGH for Cascade pattern-recognition (an LLM "fix" would have looked correct, passed review, and been silently reverted by ruff format on next CI run — the false-positive-by-LLM-eyeball failure mode is real, and the Cascade-self-correction loop here is the canonical "honest debug + queue capture" example).
  - **Methodology lesson (meta)**: The proper response to "this looks like a Python 2 leftover" is `ruff format --diff path` BEFORE editing. ~10 seconds of empirical verification saves a wrong-edit + revert cycle and produces a higher-quality queue entry. Future Cascades: when in doubt about style, ASK ruff format; don't assume.

## 2026-07-31 — horus — CI green locally / red on runner: platform-divergent typing makes `type: ignore` unsatisfiable

- **Insight**: A dependency that is **installed and `py.typed` on the dev machine but absent on the CI runner** creates a `type: ignore` that cannot be placed correctly for both environments. In HORUS, `mlx` is Apple-Silicon-only: on the Mac, mypy type-checks it, so monkey-patching `mx.set_wired_limit` *requires* `# type: ignore[assignment]`; on Linux CI the module resolves to `Any`, the ignore becomes unnecessary, and `warn_unused_ignores = true` turns it into an **error**. All three gates passed locally and CI still failed — the classic "works on my machine" that `make-sure-it-works` does not catch, because the local evidence was genuinely green.
- **Generalizable fix pattern** (two parts, neither of which suppresses a real error):
  1. Add `ignore_missing_imports = true` for the platform-specific package. It is a **no-op when the package is present**, so local strictness is unchanged; it only makes CI agree with the dev machine.
  2. **Remove the `type: ignore` entirely** by routing the dynamic patch through an `Any`-typed alias (`mod: Any = mx; mod.attr = ...`). This type-checks identically whether the module is typed or untyped. Note that `setattr(mod, "attr", ...)` and lambda assignment are *not* substitutes when `ruff` has flake8-bugbear/pycodestyle enabled (`B010`, `E731` fire) — that trades one suppression for another.
- **Broader principle worth considering for L1**: `warn_unused_ignores = true` is correct policy, but it converts optional/platform-specific dependencies into a CI-parity hazard. Any project with a platform-gated dep (CUDA-only, Apple-only, Windows-only) should prefer `Any`-alias indirection over `type: ignore` at the boundary, so the code is environment-agnostic by construction rather than by suppression.
- **Source**: `ReebalSami/horus` PR #115 → CI run 30624650035 (10 errors: 9 `import-not-found` + 1 `unused-ignore`); fix commit `05332bb`; verified green on run 30626021486.
- **Project**: horus (Cascade D). Pattern is **cross-project** — applies to any `python-ml-uv` project with a platform-gated dependency, which is the common case for local-inference ML work under `know-your-hardware`.
- **Cascade**: D
- **Date observed**: 2026-07-31
- **Proposed L1 change**: extend `know-your-hardware` (or the `python-ml-uv` L3 template's typing guidance) with a short "platform-gated dependencies must not require `type: ignore`" clause carrying the `Any`-alias pattern. Deliberately **not** proposing a new rule — this is one clause inside an existing rule's remit, per `no-quantity-over-shape`.
- **Severity**: Low-Medium. Cost was one red CI cycle and one fix commit; no data loss. Rises if a second platform-gated dep (e.g. a CUDA-only package on the rented-GPU path) reproduces it — at that point promote.
- **Pairs with**: `make-sure-it-works` (local green was real but insufficient — CI parity is part of "it works"), `know-your-hardware` (the rule that makes platform-gated deps routine in this stack), `anti-laziness-core-principles` (the lazy fix would have been `warn_unused_ignores = false` globally, discarding a genuinely useful check).

## 2026-08-04 — horus — metric core correct, reporting layer wrong: sentinel outcomes leaked into every per-field aggregate

- **Insight**: HORUS's scorer models a 5-outcome truth table (TP/FP/FN/**TN**/**EXCLUDED**) where two outcomes are deliberately signal-free, and the F1 core correctly drops both (`_aggregate_micro_macro`, `label_outcome_counts`). But **three separate reporting sites** aggregated `FieldResult.score` over *all* outcomes. Because `TN` scores 1.0 and `EXCLUDED` scores 0.0, every per-field diagnostic became a function of **how often a field happens to be absent** rather than of model quality: `rounding_amount` reported a perfect **1.000** off 29/29 TN (it was never actually tested), while `payment_means_text` reported 0.640 against a true pooled F1 of **0.286**. The headline metrics were never wrong — so nothing looked broken — yet the per-field table was about to aim a fine-tune at the wrong fields, and had already been rendered into a committed cohort heatmap figure.
- **Generalizable pattern**: whenever a metric core defines *sentinel* outcomes it deliberately excludes, the exclusion is a **cross-cutting invariant, not a local detail**. Encode it once as a named shared predicate (`SIGNAL_OUTCOMES` / `is_signal_bearing()`) and add an **agreement test** asserting the predicate matches what the aggregators actually tally — so adding a future outcome kind fails loudly instead of silently leaking into means. Three local patches would have left the fourth site to be written wrong later. Corollary: a field with **zero** signal-bearing observations must be **omitted**, never reported as 1.0 — "never asked" and "always right" must not render identically.
- **Second-order insight (the reason this is worth L1 attention)**: this is the **second recurrence of the same failure class in one milestone**. ADR-056 (three days earlier) fixed an answerability *ruler* that was measuring artifacts rather than reading quality. Both times the numbers looked plausible, both times a decision was about to be made on them, and both times the defect was in the **measuring instrument, not the system under test**. The transferable discipline: **before ranking/deciding on any derived table, validate the instrument that produced it** — cheapest check is to run the instrument against a known-perfect input (here the oracle arm) and confirm it reports ≈ ceiling. Doing that immediately exposed three fields scoring **0.000 on perfect text**, i.e. broken ground truth that would have been baked into fine-tune labels.
- **Source**: `ReebalSami/horus` branch `feat/reader-bakeoff-run`; defect at `src/horus/finetune/evaluate.py:176-177`, `src/horus/eval/harness.py:1189-1190`, `src/horus/eval/arm_b.py:288-289`; fix + evidence in `eval/per-field-reporting-audit.md`; regression tests in `tests/test_scorer.py` + `tests/test_finetune_evaluate.py`. ## 2026-08-06 — horus — a diagnostic's advisory (non-gating) channel needs the same rigour as its gate

- **Insight**: `scripts/audit_field_prompts.py` gates three checks (unfounded alias, leaked GT value, ungrounded oracle label) and reports one advisory-only check (missing-alias candidates, "LABELS SEEN, NOT LISTED"). The gating checks were rigorous from the start; the advisory channel was not, and three independent defects survived undetected because nothing failed CI on them: (1) known-set folding used raw registry text while observed labels were pre-stripped of trailing punctuation, so any alias ending in `.` (`'Steuernr.'`, `'Kunden-Nr.'`) could never match its own printed form and was reported missing; (2) `_leading_label` cannot distinguish a label from a neighbouring value on an unlabelled cell, so the raw channel proposed ground-truth ANSWERS as alias candidates (`'MUSTERLIEFERANT GMBH'`, `'IBAN DE88…'`) — the exact class of leak the channel's own sibling gate exists to reject; (3) the anchor-value lookup iterated a `set`, so which variant located a line (and therefore which label was cut) depended on CPython's string-hash order — two runs of the same script on the same corpus reported `'Liefer- und Leistungsdatum'` ×38 or ×40 depending on run.
- **Generalizable pattern**: an advisory finding is still an instruction a future session (or a future you) will act on. "It only warns, it doesn't fail the build" is not a reason to under-engineer it — a diagnostic that proposes unsafe or non-reproducible action is worse than one that proposes nothing, because it launders bad advice with the diagnostic's own credibility. Any advisory channel needs the same three properties as a gate: sound comparison (fold both sides the same way), a filter against its own known failure modes (don't propose what your sibling gate would reject), and determinism (sort before "first match wins" over any collection whose iteration order is not contractually stable).
- **Source**: `ReebalSami/horus` commit `446616a` (branch `fix/prompt-gap-classification`); fixes in `scripts/audit_field_prompts.py` (`_label_form` symmetry, `is_answer_shaped` filter, `order_needles`); regression tests in `tests/test_audit_field_prompts.py`. Discovered while re-verifying a handoff's proposed alias walk against `02fe70f`.
- **Project**: horus (Cascade D). Pattern is **cross-project** — applies to any diagnostic/audit script with a gating and an advisory tier.
- **Cascade**: D
- **Date observed**: 2026-08-06
- **Proposed L1 change**: a clause on the diagnostics/audit-script pattern (candidate home: `make-sure-it-works`, alongside the existing "validate the instrument" clauses from the 2026-08-04/2026-08-05 entries above) — *"an advisory-only finding is still evidence someone will act on; hold it to the same soundness/filter/determinism bar as a gate, or it launders bad advice with the diagnostic's credibility."*
- **Severity**: Medium. No wrong action was taken on the bad advisory output (the classification round below deliberately did not act on unverified check-C candidates), but a less careful session following the handoff's original "add these aliases" instruction would have re-introduced GT leaks and non-reproducible findings.
- **Pairs with**: the 2026-08-04 "metric core correct, reporting layer wrong" entry above (same shape: the core/gate was fine, the reporting/advisory layer was not); `anti-laziness-core-principles` (fix the channel, don't just note it's "only advisory").

## 2026-08-06 — horus — "add a prompt alias" is unsafe advice when the glossary silently drops unglossed fields

- **Insight**: `structurer.render_field_glossary` (ADR-049) emits a glossary line only for fields carrying a `description`; a field with `prompt_aliases` set but `description=None` is skipped entirely, silently. 12 of HORUS's 34 flat fields are unglossed, including `delivery_date` — the specific field a prior handoff proposed repairing by "adding the printed label as an alias". ## 2026-08-06 — horus — an arm-comparison ceiling inherits the CEILING ARM's wording, not the arm under test's

- **Insight**: Classifying a field as "reading-gap, hands off" by comparing a real-reader arm against a synthetic perfect-text ("oracle") arm assumes that if the field is at ceiling on the oracle arm, the prompt is proven adequate. It isn't, when the oracle page renders the registry's own canonical label and the real reader emits different wording for the same concept (OCR variance, publisher-specific phrasing, abbreviation). Built a per-field split of reader-arm false negatives into "value present in transcript, not mapped" vs "value absent" (`scripts/finetune_attribution.py`) specifically to close this, and it immediately contradicted the naive reading: across 34 flat fields, **56 of 84** reader-arm FNs have the value present in the transcript — i.e. two thirds of what an oracle-ceiling reading would dismiss as "the reader's fault" is actually unmapped-but-available. `seller_tax_id` is the sharpest case: at oracle ceiling (1.000) with **10** reader FNs, **7** readable, and per-invoice inspection shows **6 of those 7 print a label that is already in the prompt's alias list** while the model still answers `None`. So the residue is neither an absent value nor a missing word — it is the fine-tune's target, which is the *positive* half of the ordering rule.
- **Second-order caveat, found while auditing the above**: the readability signal is a **value-containment** test, so any field whose value legitimately coincides with another field's value inherits that field's readability. `payment_reference` shows the failure mode cleanly — 6 readable FNs, but *zero* of them print any remittance-reference label at all; the values are the invoice number repeated, which is the only reason they are "findable". The split raises suspects; it does not prove a mapping gap. Any promotion of this pattern must carry that caveat, or it will be over-read exactly the way the oracle ceiling was.
- **Generalizable pattern**: any two-arm methodology that uses one arm as a "perfect" ceiling to certify the other arm's remaining loss as unfixable must verify the ceiling arm and the test arm are asserting the SAME wording, not just the same VALUE. If the ceiling arm is synthesized (a template, a canonical rendering, a reference implementation) rather than sampled from the same distribution as the test arm, "at ceiling" proves the wording IT chose is sufficient, not that every wording the test arm can produce is covered. The fix generalizes beyond prompts: any oracle/perfect-input baseline used to attribute loss needs its own construction interrogated before its ceiling is trusted as a hands-off signal.
- **Source**: `ReebalSami/horus` commit `521ddfc` (branch `fix/prompt-gap-classification`); `scripts/finetune_attribution.py` per-field FN-readability table; cross-checked against `scripts/audit_field_prompts.py --field seller_tax_id` (`labels not listed: 0` — so the vocabulary question is closed from both directions: nothing unlisted is printed, AND the listed label IS printed on 6 of the 7 readable misses); full writeup in `docs/decisions/ADR-066-prompt-gap-classification-applied.md` §"Closing a blind spot in the oracle-ceiling inference". Numbers in this entry were corrected by a pre-merge self-audit (the first draft cited 7/6); see that ADR's §"Self-audit correction".
- **Project**: horus (Cascade D). Pattern is **cross-project** — applies to any eval methodology using a synthetic/perfect arm to certify a real arm's residual loss as out of scope.
- **Cascade**: D
- **Date observed**: 2026-08-06
- **Proposed L1 change**: a clause on `make-sure-it-works`'s "validate the instrument" family (joining the 2026-08-04/2026-08-05 entries above) — *"a synthetic 'perfect' baseline used to certify another arm's residual loss as unfixable must itself be checked for construction bias (does it assert the SAME wording/shape the real arm can produce, or only the wording the baseline's author chose?) before its ceiling is trusted."*
- **Severity**: Low-Medium here (caught within the same session, before any field was wrongly marked hands-off in a durable artifact), but structurally the same failure class as the three entries above (ruler / aggregator / reference all previously wrong in ways that looked plausible) — this is the fourth layer of the same methodology (the BASELINE ARM itself) turning up a bias, in the same milestone.
